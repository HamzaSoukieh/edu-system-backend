# Project Context

## Project Summary
- Backend for a multi-tenant Edu SaaS platform.
- One shared system supports both universities and schools.
- Each institution manages its own structure and data under tenant scope.

## Business Goal
- Let an institution onboard, configure its academic structure, manage members, and run semester-based teaching workflows.
- Keep one reusable backend instead of separate school and university backends.

## Current Architecture
- Stack:
  - Node.js
  - Express
  - MongoDB / Mongoose
- App style:
  - CommonJS
  - route -> middleware -> controller -> service -> model
- Institution-scoped business routes live under:
  - `/institutions/:institutionId/...`

## Main Entities / Models
- `User`
  - auth only
- `Institution`
  - tenant root
  - type supports `school` and `university`
- `AcademicYear`
  - shared tenant-scoped academic year record for school and university institutions
  - stores year name/date range/status
  - one active academic year is allowed per institution
  - used to resolve active/current academic-year context instead of frontends inventing ids
- `Membership`
  - institution access + role
- `MemberProfile`
  - personal/member info
- `Department`
  - current university-facing academic grouping
- `ClassLevel`
  - school academic grouping for school-side subject scope
- `SchoolClass`
  - actual school cohort such as Grade 7 A
- `ClassStudentAssignment`
  - semester-scoped school roster membership
- `Subject`
  - shared catalog item
  - university links through `departmentId`
  - school links through `classLevelId`
- `Semester`
  - semester calendar and teaching days
  - can optionally link to `AcademicYear` through `academicYearId` for migration-safe year grouping
- `Section`
  - one offered instance of a subject in one semester
- `Enrollment`
  - one student membership linked to one section
  - status-based, tenant-scoped participation record
- `SectionSession`
  - one actual dated meeting of a section
  - foundation for future attendance and QR/barcode check-in
- `Assessment`
  - one section-scoped graded item
  - may optionally link to a `SectionSession`
- `AssessmentResult`
  - one student result row for one assessment
  - anchored through existing section `Enrollment`
- `Homework`
  - one section-scoped task/workflow for homework or projects
  - may optionally link to a `SectionSession` and/or `Assessment`
- `HomeworkSubmission`
  - one current submission/manual tracking row per homework + enrollment
  - stores offline/manual submission state or private online upload metadata
  - stays separate from `AssessmentResult`, which remains the score/result row
- `SectionMaterial`
  - one section-scoped learning resource for lecture PDFs / study PDFs
  - may optionally link to a `SectionSession`
  - stores private file metadata only; files are downloaded through protected service authorization
  - stays separate from `Homework` and never creates `HomeworkSubmission` rows
- `InstitutionAcademicPolicy`
  - institution-level university academic policy
  - university-only semester-effective academic policy version
  - MVP resolves forward from `effectiveFromSemesterId` until a later policy starts
  - source of truth for outcome thresholds, GPA bands, repeat rules, academic standing rules, and semester load rules
  - graduation credit requirements are deferred to a future department/program requirement model
- `SchoolAcademicPolicy`
  - institution-level school academic policy
  - school-only promotion/result rule configuration foundation
  - supports academic-year / stage / class-level scoped resolution
  - stores grading, aggregation, failure, and promotion-rule configuration only
  - does not calculate outcomes itself; school outcome/report-card services consume the resolved policy
- `SchoolFinalOutcome`
  - school-only finalized yearly promotion/result decision record
  - stores calculated outcome snapshots separately from final decisions
  - supports manual override metadata with required reason
  - does not automatically move students to the next class level
- `InstitutionBillingProfile`
  - tenant-scoped Stripe Billing profile for one institution
  - stores Stripe customer/subscription ids and local subscription status projection
- `StripeWebhookEvent`
  - processed Stripe webhook event ids for idempotency
  - prevents duplicate webhook processing
- `ResponsibilityAssignment`
  - scoped delegated access model
  - keyed by `institutionId + userId`
  - effective responsibility permissions are resolved from the backend-defined catalog, not trusted from raw stored permission strings
  - owner/admin management APIs exist under `/institutions/:institutionId/responsibility-assignments`
  - management access is owner/admin-only and comes from institution ownership or base `Membership.role` permissions, not from scoped responsibility rows; actor membership status must explicitly be `active`
  - assignment targets must be active same-institution instructor memberships; students and admins are not eligible targets
  - create/update payloads do not accept `permissions`, membership role changes, tenant override ids, or audit actor fields
  - active scoped catalog currently grants coordinator section read, section-session read/manage, and attendance read/manage only where services enforce those scoped checks
  - head currently has allowed assignment scopes but no active operational permissions until academic/report oversight services enforce safe scoped checks
  - mentor currently has allowed assignment scopes but no active scoped permissions until student/mentor-specific service enforcement exists
  - responsibility/scope combinations are backend-defined and validated
  - used by selected section-derived read/oversight flows, not as new membership roles

  - attendance risk does not auto-drop enrollments and is not connected to GPA, percentage calculations, school promotion, university standing, or final outcomes
  - attendance oversight reads/corrections that reuse section-session scoped authorization allow coordinator section, class, department, and class-level responsibility scopes with backend-computed attendance scoped permissions
  - analytics include only closed, non-cancelled section sessions and use filtered finalized `AttendanceRecord` rows as the attendance-rate denominator

  - calculation-only school outcome service

  - returns explicit `complete` and `hasMissingResults` flags so incomplete outcomes are not presented as clean final pass/fail results

- School Promotion Dashboard APIs

  - admin/staff yearly live calculation tolerates transfers across policy semesters by using the latest resolvable active class assignment; ambiguous same-semester assignments return a normalized warning row

- School Final Outcome Foundation

  - calculated decision/reasons/warnings are stored separately from final decision/reasons/warnings
  - optional finalize-time override and later override both require a non-empty reason
  - duplicate non-cancelled final outcomes for the same institution + academic year + student are rejected in service logic
  - duplicate finalized outcomes are also protected by a finalized-only partial unique index
  - cancelled outcomes cannot be overridden
  - no class movement, next-year placement, GPA, or credit-hour behavior is introduced
- School Academic Profile Provider

  - supports student self access only when the actor is the target student membership
  - returns `finalOutcome: null` when no non-cancelled final outcome exists
  - returns top-level `excluded` explanations normalized from existing report-card warnings and incomplete completion flags
  - read-only; does not finalize, override, promote, place students, or write report-card/outcome records
- Shared Academic Profile Facade

  - delegates university profiles to `buildUniversityAcademicProfile`
  - returns `{ academicProfile: ... }`
  - provider responses can include `warnings` and `excluded` explanation arrays for incomplete or excluded academic data
  - keeps school and university calculation logic inside the institution-specific providers
  - student self route returns only the authenticated student's own profile
  - admin/staff route currently uses route-level `membership.manage` plus provider-level school `class.manage` / university `section.manage`

## Current Priorities
- Keep section design reusable across school and university.
- Avoid hard-linking Section to university-only structure.
- Keep shared services where possible.
- Prefer minimal safe changes over broad refactors.
- Use status-only lifecycle for new school modules in MVP.

## Important Constraints
- Tenant-owned data must always be filtered by `institutionId`.
- `User`, `Membership`, and `MemberProfile` stay separate by responsibility.
- One `User` may own or belong to multiple institutions.
- Only one active semester per institution.
- Keep `Subject` shared.
- Keep `Section` shared.
- Do not store `departmentId` directly on `Section`.
- For school, store `schoolClassId` on `Section` and derive roster through class assignments plus synced enrollments.
- For university filters, derive department through `Subject`.
- Keep `Enrollment` shared.
- For school, keep `Enrollment` as backend-managed technical participation data, not student self-enrollment.
- Schools do not use credit hours, GPA as the main result model, or student self-enrollment.
- School marks/outcomes reuse shared `Assessment` / `AssessmentResult` as the result source, while school policy/outcome logic stays separate from university academic policy.
- Keep `SectionSession` shared.
- `ResponsibilityAssignment` should be used only when a route has a real scope.
- School scoped academic oversight may derive through `ResponsibilityAssignment.scopeType = classLevel` when the route is tied to a school section's class level.
