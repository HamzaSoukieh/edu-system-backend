### Attendance
- `POST /institutions/:institutionId/sections/:sectionId/sessions/:sectionSessionId/attendance/open`
- `POST /institutions/:institutionId/sections/:sectionId/sessions/:sectionSessionId/attendance/qr-token`
- `PUT /institutions/:institutionId/sections/:sectionId/sessions/:sectionSessionId/attendance/manual`
- `GET /institutions/:institutionId/sections/:sectionId/sessions/:sectionSessionId/attendance/roster`
- `POST /institutions/:institutionId/sections/:sectionId/sessions/:sectionSessionId/attendance/close`
- `POST /institutions/:institutionId/sections/:sectionId/sessions/:sectionSessionId/attendance/check-in`
- `GET /institutions/:institutionId/sections/:sectionId/attendance/analytics`
- `GET /institutions/:institutionId/students/me/attendance-history`
- Current implemented rules:
  - attendance is anchored to `SectionSession`
  - assigned section instructors can list/create/generate/get/update their own section sessions through section-session service authorization, without requiring broad `section.manage`
  - only the parent section instructor can manage attendance in this step
  - attendance uses one record per enrollment per section session
  - QR flow stores only token hash + expiry in DB
  - QR tokens expire after 20 seconds and old tokens are not kept valid
  - each QR token call replaces the previous token and can be repeated while attendance stays open
  - QR token issuance and student QR check-in are only available on the scheduled local session date
  - local non-production testing can set `ATTENDANCE_QR_DATE_OVERRIDE=YYYY-MM-DD` to test QR against a teaching-day session without changing production behavior
  - student QR check-in requires active student membership + active enrolled enrollment
  - same-day QR check-in is `present` before or within the 10-minute grace window after the later of the scheduled section session start time and `attendanceOpenedAt`, and `late` after that window
  - QR check-in remains blocked after attendance is closed
  - manual attendance can still correct a closed dated session for authorized instructor/admin/derived coordinator/head access
  - scoped attendance oversight paths that reuse section-session authorization also allow:
    - the matching university department coordinator/head path
    - the matching school class-level coordinator/head path
  - roster is enrollment-based and supports:
    - `all`
    - `attended`
    - `not_attended`
    - `present`
    - `absent`
    - `late`
    - `excused`
    - `pending`
  - closing attendance creates `absent` records for still-missing enrolled students
  - logged-in students can fetch only their own tenant-scoped attendance history from existing `AttendanceRecord` rows
  - attendance history supports optional `sectionId`, `fromDate`, `toDate`, and `status` filters
  - attendance history response stays record-first and includes lightweight nested `session`, `section`, and `subject` summaries plus a filtered summary count block
  - section-level attendance analytics are available to:
    - admin
    - the parent section instructor
    - derived university department coordinator/head through the same safe scoped oversight path already used for section session status changes
    - derived school class-level coordinator/head through the parent section class level
  - students cannot access attendance analytics
  - attendance analytics include only section sessions that are both:
    - `attendanceState = closed`
    - `status != cancelled`
  - attendance analytics support optional `fromDate` and `toDate` filters against `SectionSession.sessionDate`
  - attendance analytics remain finalized-record-based for MVP:
    - `late` counts as attended
    - `late` remains separate from `present`
    - `excused` remains separate from `absent`
    - `attendanceRate = attendedCount / totalCount`
    - `totalCount` uses only the filtered finalized `AttendanceRecord` rows tied to eligible section sessions
  - section analytics now applies existing `Institution.policies` attendance fields as response-only risk signals:
    - `warnAfterAbsences`
    - `dropAfterAbsences`
    - `lateToAbsenceRatio`
    - `excusedCountsAsAbsence`
  - attendance analytics normalizes `lateToAbsenceRatio` to a whole integer `>= 1`; fractional, zero, null, string, or missing values fall back to the default
  - analytics response includes `attendancePolicySummary` plus per-student `attendanceRisk`
  - `effectiveAbsences = absentCount + floor(lateCount / lateToAbsenceRatio) + excusedCount` only when excused absences count by policy
  - `attendanceRisk.status` is `good`, `warning`, or `drop_risk`; `drop_risk` wins over `warning`
  - attendance risk does not auto-drop enrollments, change subjects, affect GPA/percentages, affect school promotion, affect university standing, or write final outcomes
  - Postman manual testing pack is available in `postman/attendance.postman_collection.json` with template and local environments
- Still missing:
  - broader attendance reporting beyond section-level finalized analytics
  - broader attendance oversight flows beyond the current safe scoped read/correction paths
  - TODO/verify: duplicate-aware drop-risk escalation/notification to the appropriate higher role

### Academic Policies / University Registration Foundation

- Current implemented rules:
  - university-only institution-level academic policy lives in a dedicated model
  - implementation files are university-prefixed internally, but existing route URLs stay unchanged for API compatibility
  - policy versions are effective by semester using `effectiveFromSemesterId` only in MVP
  - a partial unique index allows only one `active` policy per institution + `effectiveFromSemesterId`
  - resolvable `active|archived` policy resolution stays deterministic by start semester within the same institution
  - policy configuration validates coherent outcome thresholds, contiguous GPA bands, overload max >= default max, and overload GPA within the configured scale
  - policy now stores university-only `repeatPolicy`:
    - `enabled`
    - `gpaCalculationMethod`
    - `earnedCreditsMethod`
    - `prerequisiteMethod`
    - `allowGradeImprovementRepeats`
    - `blockRepeatAfterFinalPass`
  - policy now stores university-only `academicStandingRules`:
    - `enabled`
    - GPA `bands` for `good_standing`, `academic_warning`, `probation`, and `suspension`
    - `allowedToContinue`
    - `requiresAdvisorReview`
    - `requireManualReviewIfIncompleteProfile`
    - `noOutcomeStanding`
    - `allowManualReview`
  - old policy records without `repeatPolicy` resolve to defaults:
    - GPA: `best_attempt_only`
    - earned credits: `count_once_per_subject`
    - prerequisites: `best_passed_attempt`
    - grade-improvement repeats allowed
    - final-pass repeats blocked
  - explicit legacy behavior is available by configuring `gpaCalculationMethod=all_attempts` and `earnedCreditsMethod=count_each_passed_attempt`, or by setting `repeatPolicy.enabled=false`
  - old policy records without `academicStandingRules` resolve to defaults:
    - GPA >= 2.0: `good_standing`
    - 1.7 <= GPA < 2.0: `academic_warning`
    - 1.0 <= GPA < 1.7: `probation`
    - GPA < 1.0: `suspension`
    - no finalized outcomes: `no_standing_yet`
    - incomplete official profile data can return `review_required`
    - GPA exactly at the GPA scale maximum matches the top standing band
  - policy stores blocking `minimumEnrollmentCreditHours` rather than warning-only `minCreditHours`
  - `InstitutionAcademicPolicy` does not store graduation required credits; that is deferred to a future department/program requirement model
  - dangerous academic-field edits are blocked once the policy is already used by finalized outcomes
  - central resolver now loads the correct policy for a given institution + semester
  - internal academic outcomes now derive from:
    - closed sections
    - published section assessment weight total = 100
    - per-enrollment published assessment results
    - resolved semester policy
    - strict exclusion of incomplete or invalid finalized inputs for a student's closed-section outcome
    - stable per-subject repeated-attempt summaries so eligibility can reuse consistent prior-subject meaning
    - repeat-policy official GPA inclusion/exclusion for repeated finalized attempts
    - repeat-policy earned-credit counting for repeated passed attempts
    - structured `excluded` explanations for safely detectable non-official inputs such as open sections, unpublished or incomplete assessments, missing results, missing policy, and invalid credit hours
  - internal university academic profile provider now composes the existing academic outcome summary into a transcript-style read model for the shared academic profile facade
  - the internal provider remains read-only, university-only, tenant-scoped, staff-readable through current `section.manage` access, and self-readable only through the shared facade's target-student check
  - university academic profile responses surface deduped/sanitized outcome-service `excluded` explanations and repeat-policy GPA/credit classifications
  - university `subjectAttempts` now include repeated-attempt display fields:
    - `attemptNumber`
    - `attemptCount`
    - `isRepeatedSubject`
    - `isLatestAttempt`
    - `isBestAttempt`
    - `previousAttemptCount`
    - `hasPreviousAttempt`
    - `attemptLabel`
  - university `subjectOutcomeSummaries` now include decorated transcript fields such as subject code/name, compact attempt rows, best/latest outcome ids/status/percentage, and repeat-history booleans like `failedThenPassed`, `passedThenRepeated`, and `repeatedAfterFinalPass`
  - university profiles now include active `repeatPolicy`, `gpaCalculation`, and `earnedCreditCalculation` notes
  - university profiles now include live/read-only `academicStanding` with standing, continuation/advisor-review flags, reason codes, applied band, and calculation source
  - `section_not_closed` profile explanations remain visible, but do not by themselves force `academicStanding.standing=review_required` when finalized GPA exists
  - university `subjectAttempts` and compact summary attempt rows show `includedInOfficialGpa`, repeat-policy exclusion reason codes, and earned-credit counted/excluded flags
  - TODO/verify: `semesterId` is accepted and validated by the provider, but filtering is documented as not applied until the university outcome service supports a semester-scoped source contract
- the self-enrollment preview route now loads tenant-scoped context in `enrollmentService` and delegates shared rule evaluation to an internal reusable eligibility decision service
- the self-enrollment browse route now reuses the same shared decision engine for lightweight per-row `eligibilitySummary` without forcing the full preview payload into every list item
- the self-enrollment submission write route now reuses the same shared decision engine as a thin safe layer before creating shared `Enrollment` rows
- the preview response now acts as the canonical explanation surface with:
